## The SQL injection alert

ZAP saw a different response between its true and false payloads and flagged it. Checked three ways:

- **By hand on `company`:** true, false and `OR` payloads get the same `not_found` answer. The message quotes the input back, which is what the scanner compared.
- **Replay:** 18 of the 49 requests carry the value in the URL. Each was replayed with `AND` true, `AND` false and `OR` conditions. All 18 gave identical answers once the payload text was removed, all 400 or 404. The other 31 are in request bodies and weren't replayed.
- **Code:** every query goes through Kysely with bound values. A search of `sql.raw`, `sql.lit`, `sql.ref` and string-built queries found no request input in any of them; they hold fixed names, numbers and our own file paths.

YARA and schema checks look at definitions, not behavior. They can't show that a tool does only what it says.

## What the scans covered less well

- **MCP:** ZAP's fuzzing mostly stopped at the JSON-RPC layer (159 rejected bodies), and `tools/list` hit our rate limit. So a separate script sent 416 hostile values through the 26 read-only tools (SQL, script, path and template strings). All returned 200 with no database error or stack trace. Write tools weren't fuzzed this way.
- **Access between workspaces:** one account can't test this. The red-team suite covers it, and a clinic test should too.
- **Rate limits** may have blocked some probes. That's the protection working, but it reduces coverage.
